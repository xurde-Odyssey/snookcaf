# Architecture and delivery plan

## Phase 1 foundation (preserved)

Create a responsive application shell, UI primitives, preview dashboard, database setup, and tooling. No business write APIs, authentication claims, live timers, payment controls, or real financial dashboards.

Files: `src/app`, `src/components`, `src/features/dashboard`, `src/lib`, `src/providers`, `prisma`, test configuration, and setup documentation. Models: Business and versioned BusinessSettings. Dependencies: Next.js App Router, TypeScript, Tailwind CSS, shadcn patterns / Radix primitives, Lucide, PostgreSQL / Prisma, TanStack Query, React Hook Form / Zod, Recharts, Vitest, Playwright.

Acceptance criteria:

- Dark desktop sidebar; accessible mobile navigation; light content with restrained orange accents.
- Eleven working destinations, clearly marking future operations as planned.
- Reusable KPI, status, data table, empty state, modal, and button patterns.
- Labeled sample data, frozen sample timers, usable filters/search/dialogs and empty-state toggle.
- Loading, error recovery, keyboard focus, semantic tables, and narrow-screen overflow handling.
- NPR / Kathmandu display defaults, UTC timestamp persistence, migration and development-only seed.
- Lint, typecheck, relevant tests, Prisma validation, and production build verified when dependencies and runtime are available.

## Modular monolith direction

Keep route handlers thin. Future feature services belong in `src/features/<domain>/server` and own authorization, validation, business calculations, and database transactions. Shared client components do not import Prisma. `src/lib/db.ts` is marked server-only. The UI currently imports isolated fixtures directly so no fake operational API is introduced.

Financial phases must use decimal-safe arithmetic, original-price snapshots, auditable ledgers and database-enforced concurrency constraints. An in-memory timer or client-side price must never become authoritative. A future active-session partial unique index, idempotency keys, and transaction isolation require database-backed integration tests when implemented.

BusinessSettings is versioned from the start. There is no settings mutation endpoint yet. Identity now has staff actors and audit events. Future settings mutations must include their actor and audit event; when pricing arrives, snapshot tariff settings on sessions. Do not populate placeholder models for unfinished domains just to imply completeness.

## Phase 2 implementation

Identity models are separate from operational domains: Staff, Session, LoginRateLimit and AuditLog. Server-only shared authentication services live in `src/lib/auth`; staff writes in `src/features/staff/server` enforce permissions and business scope within locked transactions. Next page guards and API handlers share this layer. Password hashing uses native Node Argon2id (Node >=24.7). No external identity provider, JWT, public signup, or browser-managed tokens are introduced.

The `(workspace)` route group preserves all existing URLs and shell components. Login and forced-password-change pages render outside the shell. Each operational page authorizes independently, and navigation filters the same central policy. Owner/admin/manager sample dashboards remain; cashier/staff get an overview without reporting. Staff and audit are the only newly operational business pages.

See [permissions and security design](permissions.md), [file inventory](phase2-files.md), and [actual verification results](verification.md). Database and browser acceptance remain pending in this sandbox.

## Remaining phases

3. Tables, tariffs, reservations, server-timed sessions and concurrency constraints.
4. Menu, variants, cart drafts, price snapshots and order lifecycle.
5. Unified billing, settlement, refunds, receipt compliance review and idempotency.
6. Inventory ledgers, recipes, suppliers, purchases and expenses.
7. Customers, memberships and shifts (staff identity is implemented in Phase 2).
8. Transaction-backed analytics, reconciliation and exports.
9. Security and integrity tests, monitoring, backup/restore and deployment procedures.

Hosting and production deployment remain outside this implementation. No compliance-ready invoices are generated by this foundation.


## Phase 3 implementation

Play sessions use `SnookerSession`, distinct from authentication `Session`. `src/features/snooker/server/service.ts` owns transactional catalog/session mutations and reuses the business-row lock for consistent authorization and lifecycle transitions. Rate versions and segments retain Decimal snapshots; proposals and approvals are distinct records; checkout is outstanding only. Raw SQL supplements Prisma with exclusion, partial-unique and deferred consistency constraints and history-protection triggers. See [the Phase 3 design](phase3.md) for the implemented scope and [verification](phase3-verification.md) for pending runtime acceptance. Café ordering and payments remain future phases.
